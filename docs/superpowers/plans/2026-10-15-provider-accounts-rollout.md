# Provider Accounts Rollout and VPS Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish the approved provider-account and visual updates to the existing VPS only after recording the current state, preserving VPS-specific changes, and preparing a verified rollback path.

**Architecture:** Treat rollout as a staged operation after the four implementation plans pass. Compare the deployment target with the canonical dashboard and API outputs, back up affected files and database state, apply the additive account migration, then verify actual API and provider health. Use only configured, non-embedded deployment credentials.

**Tech Stack:** Existing VPS deployment stack, Node.js 22+, Prisma, PostgreSQL, Docker, Playwright, PowerShell.

**Spec:** `docs/superpowers/specs/2026-10-15-provider-accounts-and-platform-visual-design.md`

**Dependencies:** Complete `2026-10-15-provider-account-storage-oauth.md`, `2026-10-15-provider-account-routing-usage.md`, `2026-10-15-provider-accounts-dashboard.md`, and `2026-10-15-platform-branding.md` first.

## Global Constraints

- A migração será aditiva e idempotente.
- Antes da publicação, salvar backup reversível e comparar a tela com a VPS; depois da publicação, confirmar a API real e que “Online” depende de teste bem-sucedido.
- Configurações sem conexão utilizável continuarão aparecendo como provedores disponíveis, sem criar uma conta conectada fictícia.
- A interface nunca receberá valores de segredo; respostas administrativas exporão somente indicadores como “credencial salva” ou “precisa reautorizar”.
- Credenciais, códigos OAuth e tokens não aparecem em respostas, HTML, logs ou erros.

## Review Focus

- The VPS contains a custom dashboard difference that is absent from the checkout (`provider-accounts-rollout.md`: compare route behavior and preserve the custom hunk in the deploy artifact).
- A database backup is missing, empty, or unreadable (`provider-accounts-rollout.md`: verify a nonzero dump and inspect its catalog before migration).
- The deployment target is unreachable or only an embedded credential is available (`provider-accounts-rollout.md`: stop before mutation and report the configured access requirement).
- The backfill creates no connection for a provider without usable credentials and creates one account for each valid legacy connection (`provider-accounts-rollout.md`: compare pre/post counts and safe account views).
- An account appears online without a successful health call or a real inference check fails after rollout (`provider-accounts-rollout.md`: live health and inference smoke checks).

### Task 1: Capture the checkout, runtime, and VPS differences

**Files:**

- Create: `docs/releases/2026-10-15-provider-accounts-release.md`
- Read: `AGENTS.md`, `PROJECT_RULES.md`, `TODO-BUGS.md`, `docs/AUDITORIA_FRONT_PRODUCAO_2026-09-08.md`
- Read: the configured VPS dashboard/API deployment targets without exposing secrets

**Interfaces:**

- Release record contains branch, commit SHA, build result, runtime status, affected files, and a list of VPS-only hunks; it contains no secret values.
- Deploy artifact is generated by applying the reviewed feature diff to the VPS version or by preserving each verified VPS-only hunk in the canonical result.

- [ ] **Step 1: Record the current state** with `git branch --show-current`, `git rev-parse HEAD`, the dashboard/API build state, and the live health endpoint responses.
- [ ] **Step 2: Compare every affected file** with the VPS copy and record a line-level merge plan for VPS-only changes; verify provider routes and shell actions survive the merge.
- [ ] **Step 3: Review project rules and known blockers** in the required repository documents; confirm the deploy path does not rely on an embedded production secret.
- [ ] **Step 4: Build the merged deploy artifact** and run `npm run build`, `npm run lint`, focused provider/API tests, and the production-front audit against the target when reachable.
- [ ] **Step 5: Inspect the artifact diff** and verify it contains only the approved feature plus preserved VPS-specific changes.

### Task 2: Create and verify rollback backups

**Files:**

- Create: a timestamped backup directory outside the application release directory, containing original affected files and deployment metadata
- Create: a compressed PostgreSQL dump in the protected backup location

**Interfaces:**

- File backup records original paths and checksums so the old release can be restored without reconstructing files.
- Database backup can be read by the configured PostgreSQL restore tooling and is stored outside the web root with restricted permissions.

- [ ] **Step 1: Verify disk space and backup destination permissions** on the target.
- [ ] **Step 2: Copy every affected VPS file** and record its checksum before changing the release.
- [ ] **Step 3: Create the database dump** using the configured production connection without printing its credentials.
- [ ] **Step 4: Validate the dump** by checking its size, listing its schema objects, and restoring it into a disposable database when available.
- [ ] **Step 5: Verify rollback commands** point only to the timestamped backup and document the exact prior deployment revision.

### Task 3: Apply the additive migration and release

**Files:**

- Deploy: API, worker, shared package, and dashboard artifacts from the reviewed release
- Modify: `docker/api.Dockerfile` or the verified deployment entrypoint to use an additive schema command without `--accept-data-loss`
- Modify only on target: database schema through the approved additive migration procedure

**Interfaces:**

- The account backfill is idempotent and can be rerun without duplicating accounts.
- Production migration must not use a command that accepts destructive schema changes; it preserves provider defaults, models, logs, and historical usage.
- Deployment credentials come from an approved environment or SSH configuration and are never embedded in commands or source files.

- [ ] **Step 1: Run the migration in validation mode** against a production-shaped disposable database and compare provider/account/model counts.
- [ ] **Step 2: Apply the additive schema command without `--accept-data-loss` and run the idempotent backfill** only after the verified backup exists.
- [ ] **Step 3: Deploy the API and worker**, wait for readiness, and confirm all pre-existing health checks pass.
- [ ] **Step 4: Deploy the merged dashboard artifact** while retaining the backup and preserving each VPS-only hunk from Task 1.
- [ ] **Step 5: If safe deployment access is unavailable**, stop before any production mutation and report the missing access configuration; do not invoke a deploy script that contains embedded credentials.

### Task 4: Verify live behavior and rollback readiness

**Files:**

- Modify: `docs/releases/2026-10-15-provider-accounts-release.md` (final verification and rollback result)
- Test: live API health, provider-account admin endpoints, and dashboard routes

**Interfaces:**

- Live checks use existing authenticated admin/API flows and do not include credential values in saved output.
- “Online” is accepted only after a successful health test against the configured provider endpoint.

- [ ] **Step 1: Verify the backfill** returned one account per usable legacy connection, preserved provider defaults and models, and returned no secret fields.
- [ ] **Step 2: Verify dashboard routes** for providers and branding at desktop and 390 × 844; confirm VPS-specific actions and navigation remain available.
- [ ] **Step 3: Perform a real provider health test** and one authorized inference call; confirm only successful health is shown as online and per-account usage is attributed correctly.
- [ ] **Step 4: Verify OAuth/API-key options** according to configured provider credentials, and ensure responses and logs contain no secrets.
- [ ] **Step 5: Record final health/build/test evidence** and the rollback result; retain the backup through the agreed stabilization window.
